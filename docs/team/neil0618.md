# Neil Mande - Project Portfolio Page

## Overview

### Project: MishMash

MishMash is a Java command-line meal-prep planner. Users can manage recipes, generate meal plans and grocery lists, and track nutrition against their targets.

### Enhancements implemented

- **New feature: Deleting recipes (`delete-recipe`).**
    - **What it does:** Deletes the recipe at a displayed index after asking the user to confirm, then reports the deleted recipe's name and how many recipes remain.
    - **Justification:** Deletion cannot be undone, and recipe numbers shift after every delete, so a mistyped index can remove the wrong recipe. Users need to see what they are about to delete.
    - **Highlights:** Added a `confirmationPrompt` extension point to the `Command` interface (default: no prompt) and the confirmation flow in `MishMash`, so any command can ask a yes/no question before it runs. The prompt names the recipe and is built only after the index is checked, so an invalid index is reported without asking. Only `y` or `yes` counts as agreement; anything else, including the end of input, cancels. Added `RecipeBook.remove(int)`, which keeps the order of the remaining recipes and identifies recipes by position because names can repeat. The confirmation hook was later reused by the plan-replacement confirmation in `generate-plan`.
    - **Evidence:** [#25](https://github.com/AY2627S1-CS2113-W13-4/tp/pull/25).

- **New feature: Listing recipes (`list-recipes`).**
    - **What it does:** Lists every recipe with its number and calories, or shows one recipe in full with `list-recipes INDEX`.
    - **Justification:** Commands such as `delete-recipe`, `edit-recipe` and `record-meal` ask for a recipe's number, so users need a read-only way to find it and to check a recipe before changing it.
    - **Highlights:** Reused the shared recipe viewer for the single-recipe view so it matches the `add-recipe` confirmation. Wrote the recipe-index parsing, which accepts digits only, so signs, decimals, extra words and overflowing numbers are rejected with recoverable errors; it was later reused by `edit-recipe` and `record-meal`. Listing never changes the recipe book.
    - **Evidence:** [#29](https://github.com/AY2627S1-CS2113-W13-4/tp/pull/29).

- **New feature: Saved daily targets (`set-targets`, `view-targets`).**
    - **What it does:** Saves daily calorie, protein, carbohydrate and fat targets for the session. `set-targets` updates only the fields given, in any order, and `none` removes a target (for example `set-targets cal/2000 p/none`). `view-targets` shows what is saved. A later `generate-plan` uses the saved targets for any nutrient left out of the command, and targets typed in `generate-plan` take priority.
    - **Justification:** Users aim for the same daily targets every time; retyping them on each `generate-plan` is repetitive and easy to get wrong. Delivers issues [#55](https://github.com/AY2627S1-CS2113-W13-4/tp/issues/55) and [#56](https://github.com/AY2627S1-CS2113-W13-4/tp/issues/56) as one feature, since the calorie target is simply a fifth number alongside the macros.
    - **Highlights:** Modelled each field as keep, replace or clear (`TargetChanges`), so omitting a field and writing `none` are different instructions. Added a `Nutrient` enum and a per-nutrient merge (`NutritionTargets.overriddenBy`) so typed values win over saved ones. `generate-plan` reads the shared `TargetSettings` when it runs, so a later `set-targets` is respected, and with nothing saved it behaves exactly as before. The merged request is the one stored with the plan, so `view-plan` warnings and `set-diet` repair use the targets that were actually applied rather than only those typed. Success and failure messages say when saved targets were used, and tell the user to change them with `set-targets`.
    - **Evidence:** [#86](https://github.com/AY2627S1-CS2113-W13-4/tp/pull/86).

### Testing and code quality

Added dedicated JUnit test classes for `delete-recipe`, `list-recipes`, `set-targets`, `TargetChanges`, the `set-targets` parser and the targets handling in `Parser`, plus extra cases in `RecipeBookTest`, `ParserTest` and `MishMashTest`. Tests cover first, last and repeated indexes, duplicate recipe names, empty books, out-of-range indexes leaving the book unchanged, confirmation prompts that name the recipe, deletion cancelled at the end of input, index parsing boundaries (extra whitespace, leading zeros, the largest integer, invalid arguments showing only that command's usage), CLI transcripts for both commands, partial updates, clearing with `none`, typed-over-saved merging, saved targets read at execution time, and the new messages in `generate-plan`. Following review feedback on [#86](https://github.com/AY2627S1-CS2113-W13-4/tp/pull/86), removed a redundant validation check from `TargetChanges` and added the saved-target messages to `generate-plan`, with tests. Evidence: [#25](https://github.com/AY2627S1-CS2113-W13-4/tp/pull/25), [#29](https://github.com/AY2627S1-CS2113-W13-4/tp/pull/29), [#86](https://github.com/AY2627S1-CS2113-W13-4/tp/pull/86).
